- `site.jurisdiction` 이 발송 규칙을 결정합니다 — 사업장 추가 시 관할 규칙만 정의하면 되도록 설계
- **로그인 화면의 사업장 드롭다운은 이 표에서 생성됩니다.** 사업장 추가 시 코드 수정 없이 반영되어야 합니다

## 2. 권한 레벨

기획안 명시: Staff / Site Administrator / System Administrator

| 레벨 | 대상 | 데이터 범위 |
|---|---|---|
| **Staff** | 일반 영업담당자 | **현재 세션의 사업장** 데이터 |
| **Site Administrator** | 사업장 책임자 | 현재 세션의 사업장 전체 + 사업장 내 사용자 관리 |
| **System Administrator** | 시스템 관리자 (FRH 소속 예상) | 전 사업장 + 시스템 설정 |

> **겸직 시 역할은 사업장별로 결정됩니다.** 같은 사람이 FRH 에서는 Staff, FRK 에서는 Site Admin 일 수 있으며, 적용되는 역할은 **로그인 시 선택한 사업장**의 것입니다.
>
> System Administrator 는 사업장에 종속되지 않는 전사 권한입니다 (`app_user.is_system_admin`).

## 4. 정책 결정이 필요한 항목

**4-1. 고객 데이터 내보내기를 Staff에게 허용할 것인가**
기획안의 문제 #4는 "퇴사 시 연락처가 함께 사라진다"는 것이지만, 반대 위험도 있습니다. Staff가 전체 고객 목록을 Excel로 내려받을 수 있으면 FCM이 해결하려던 "통제되지 않은 스프레드시트"가 그대로 재생산됩니다. 선택지:
- 내보내기를 Site Admin 이상으로 제한
- Staff는 허용하되 내보내기 행위를 감사 로그에 남기고 건수 상한 설정
- 완전 금지 (업무 불편 가능)

**4-2. 대량 발송에 승인 절차가 필요한가**
공용 계정 `sales@frankoniagroup.com` 하나로 전 사업장이 발송하므로, 한 사람의 실수가 도메인 평판 전체에 영향을 줍니다. 일정 수(예: 200건) 초과 시 Site Admin 승인을 요구할지 결정 필요.

**4-3. Staff가 동료의 안건을 볼 수 있는가**
- 볼 수 있음 → 사업장 내 중복 영업 방지에 유리 (기획안 문제 #2)
- 볼 수 없음 → 개인 실적 노출 우려 해소

사업장 **간** 중복 영업은 완전 격리 확정으로 수용하기로 했으므로(§4-6), 기획안 문제 #2 에 대응할 수 있는 유일한 범위가 **사업장 내부**입니다. 여기서도 격리하면 문제 #2 는 전혀 해결되지 않습니다.

> 현재 다른 문서들은 **"사업장 전체 공유"** 를 가정하고 작성되어 있습니다. 이 가정이 틀리면 `05-인증접근제어.md` §0 과 함께 수정이 필요합니다.

**4-4. 한 사용자가 여러 사업장에 속할 수 있는가** — ✅ **확정: 겸직 가능**
관리자가 사업장별로 권한을 부여하는 방식입니다. 데이터 모델은 `user_site_membership` 중간 테이블로 반영 완료했으며, `app_user` 에서 `site_id` 와 `role` 을 제거했습니다.

- 역할은 **사업장별로 다를 수 있습니다** (FRH 에서는 Staff, FRK 에서는 Site Admin)
- 세션당 활성 사업장은 **1개**이며, 전환하려면 재로그인해야 합니다
- 선택한 사업장에 활성 권한이 없으면 **로그인 자체가 실패**합니다 (→ `05-인증접근제어.md` §2-3)

**4-5. System Administrator 는 누구인가**
전 사업장 개인정보에 접근 가능한 최고 권한입니다. FRH 소속으로 예상되나 지정 인원과 인원수(최소 2명 권장 — 1명이면 부재 시 시스템 잠김) 확정 필요.

로그인 절차와 전사 조회 경로는 `05-인증접근제어.md` §2-5 에 정의되어 있습니다. 요지는 **평소에는 일반 사용자와 동일하게 한 사업장만 보이고, 전사 조회는 별도 관리 콘솔에서 건별 감사 기록과 함께 이루어진다**는 것입니다.

**4-6. 사업장 간 고객 가시성** — ✅ **확정: 완전 격리**
각 사업장 영업담당자는 자기 사업장 고객만 확인·관리합니다. 사업장 간 중복 영업은 **구조상 수용**하며 해결 대상이 아닙니다. 전역 식별자를 통한 중복 표시안은 채택하지 않았습니다.

기획안의 문제 #2("같은 고객을 두 사람이 모른 채 영업")는 이에 따라 **사업장 내부**에 한정해 대응합니다 → §4-3 참조.

**4-7. 신원 계정 생성 주체** *(잠정)*
현재 매트릭스는 **신원 계정 생성·비활성화를 System Admin 전용**으로, **사업장 권한 부여·회수를 해당 사업장 Site Admin** 으로 두었습니다.

겸직 구조이기 때문에 이 분리가 필요합니다. Site Admin 에게 계정 생성까지 허용하면, FRK 의 Site Admin 이 만든 계정에 FRH 권한을 붙이는 경로가 생길 수 있습니다. 계정이라는 신원 자체는 전사 자산으로 두고, 사업장 권한만 각 사업장이 관리하는 편이 경계가 명확합니다.

다만 실무상 System Admin 이 모든 신규 입사자 계정을 만들어야 하는 부담이 생기므로, 운영 규모를 보고 조정할 수 있습니다. **확인 요망.**

## 5. 격리 구현 시 유의점

- 격리는 **DB 레벨 강제**가 요구사항입니다 (기획안 "enforced at the database level"). 애플리케이션 조건절만으로는 요구를 충족하지 못합니다
- PostgreSQL Row Level Security 를 쓰면 세션 변수에 `site_id` 를 설정하고 정책으로 강제할 수 있어 요구 문구에 정확히 부합합니다
- MySQL 에는 동등 기능이 없으므로 DB 선택 시 이 요구사항을 함께 검토해야 합니다
- System Admin 의 전사 조회는 RLS 우회 경로가 되므로, 이 경로의 접근은 반드시 감사 로그에 남겨야 합니다. 대응 엔티티는 `03-데이터모델초안.md` §5-A `audit_log` 이며, `actor_site_id ≠ target_site_id` 조건이 우회 접근을 식별합니다
- 인증·세션·주소 직접접근 차단의 상세 명세는 `05-인증접근제어.md` 에 있습니다
- 격리 대상 테이블은 모두 `site_id` 를 직접 보유합니다 — `contact`, `company`, `consent_event`, `send_log`, `followup_entry`, `opportunity`, `campaign`, `segment`, `import_batch`, `email_template`, `data_subject_request` (11개). 조인을 거쳐야 소속을 알 수 있는 테이블에는 RLS 정책을 걸기 어렵기 때문입니다
- **예외 2개** — `audit_log` 는 `actor_site_id` / `target_site_id` 두 개를 가지며 RLS 는 `target_site_id` 기준입니다. `system_setting` 은 전사 단일이며 System Admin 전용입니다
- RLS 를 실제로 작동시키려면 `FORCE ROW LEVEL SECURITY` 와 `SET LOCAL` 사용이 전제입니다 (→ `05-인증접근제어.md` §4, 구현 상세는 `07-기술스택.md` §3)
