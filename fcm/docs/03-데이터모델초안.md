# FCM 데이터 모델 초안

> 상태: 초안 · 갱신 2026-08-26
> 확정 전 검토용입니다. 특히 §6 미결 사항이 정해지기 전에는 스키마를 고정하지 마십시오.
>
> **표기 규율** — 이 문서의 테이블·필드는 대부분 기획안에서 직접 도출한 것이 아니라 요구사항으로부터 설계한 `[도출]` 결과물입니다. 기획안이 명시한 것은 필수 6개 필드(Name, Email, Company, Category, Language, Country), 사업장 격리, 동의 추적, 발송 이력, 7일 경고, 권한 3단계뿐입니다.
>
> 본문의 예시(현대차 관련 등)는 기획안이 아니라 사내 기존 자료에서 가져온 참고 사례입니다.

## 1. 설계 원칙

1. **사업장 격리는 애플리케이션이 아니라 DB가 강제한다** — 기획안의 "enforced at the database level" 요구를 그대로 구현. 애플리케이션 코드의 `WHERE site_id = ?` 는 빠뜨리면 무너지므로 신뢰 대상이 아님
2. **동의는 상태가 아니라 이력이다** — 현재 동의 여부만 저장하면 "언제 어떤 근거로 동의받았는가"를 입증할 수 없음. GDPR 입증 책임 대응
3. **발송 이력은 불변 기록이다** — 고객이 삭제되어도 "무엇을 보냈는가"의 사실은 남아야 함
   → 따라서 `contact` 영구 삭제 시 `send_log.contact_id` 와 `consent_event.contact_id` 는 `ON DELETE SET NULL` 로 처리합니다. `send_log.contact_email_snapshot` 도 함께 비웁니다(개인정보 삭제 요청의 취지). 발송 건수·시각·캠페인 연결은 남고 **누구였는지만 지워집니다** — F-5(삭제 요청)와 원칙 3을 동시에 만족시키는 유일한 지점입니다
4. **고객사와 담당자는 분리한다** — 한 회사에 여러 담당자가 있고(사내 기존 자료의 현대차 전자신뢰성시험팀 2인 사례), 담당자는 이직하지만 회사는 남음
5. **사용자의 소속은 사업장별 권한 부여로 표현한다** — 겸직이 가능하므로 사용자 테이블에 사업장을 넣을 수 없습니다
6. **격리 대상 테이블은 모두 `site_id` 를 직접 보유한다** — 조인을 거쳐야 소속 사업장을 알 수 있는 구조는 Row Level Security 정책을 걸기 어렵고, 조인 경로가 끊기면 격리도 함께 무너짐

## 2. 엔티티 개요

```
app_user ─── user_site_membership ─── site   (겸직: 1인 다사업장)
app_user ─── user_session ── (site_id 고정)

site ─┬────────────────────────────────┐ (owner / created_by)
      │                                │
      ├─ company ─┬─ contact ─┬─ consent_event
      │           │           ├─ send_log ─── campaign ─── segment
      │           │           └─ (opportunity.primary_contact_id)
      │           └─ opportunity ─── followup_entry
      │
      ├─ import_batch ──→ contact (일괄 등록 출처)
      ├─ email_template ──→ campaign
      ├─ audit_log
      └─ data_subject_request ──→ contact
```

>
> 감사 로그는 append-only 이며 System Admin 도 수정·삭제할 수 없어야 합니다. 그렇지 않으면 감사 기록으로서 의미가 없습니다
>
> **원칙 6의 유일한 예외:** `audit_log` 는 단일 `site_id` 를 갖지 않습니다. 사업장 경계를 넘는 행위를 기록하는 것이 목적이므로 `actor_site_id` 와 `target_site_id` 두 개를 보유합니다. RLS 정책은 `target_site_id` 기준으로 겁니다 — Site Admin 은 "자기 사업장 데이터에 무슨 일이 있었는가"를 봐야 하며, 여기에 System Admin 의 타 사업장 접근 기록이 포함되어야 감시가 성립합니다
>
> `actor_site_id` 가 NOT NULL 이어야 하는 이유: NULL 이면 SQL 에서 `NULL <> 'FRH'` 는 참이 아니라 NULL 로 평가되어, **우회 접근이 탐지 필터에 잡히지 않습니다.** F-6 을 P0 으로 올린 근거가 통째로 무력화됩니다

## 6. 미결 사항 — 결정 전 스키마 확정 금지

**6-1. 사업장 간 고객 중복** — ✅ **확정: (a) 완전 분리**
같은 회사가 FRH와 FRK 양쪽 고객이면 **각 사업장이 독립된 레코드를 보유**하며 서로 알지 못합니다. 사업장 간 중복 영업은 구조상 수용합니다.

전역 식별자(`global_contact`) 도입안은 채택하지 않았습니다. 따라서 `contact` 의 `UNIQUE (site_id, email_normalized)` 제약이 최종이며, 사업장 간 동일 이메일은 정상입니다.

**6-2. 격리 구현 방식** — ✅ **확정: PostgreSQL + RLS**
MySQL·MariaDB 에는 동등 기능이 없어 "DB 레벨 격리" 요구를 충족할 수 없으므로 PostgreSQL 로 확정했습니다.

RLS 를 실제로 작동시키는 4가지 전제(`FORCE ROW LEVEL SECURITY`, 비소유 롤 접속, fail-closed `current_setting`, `SET LOCAL`)는 `07-기술스택.md` §3 에 구현 수준으로 정리되어 있습니다. 사업장별 스키마 분리안은 검토 후 보류했으며, 데이터 소재지 분리가 필요해지면 재검토합니다.

**6-3. phase 값 정의** — 예: `inquiry` / `proposal` / `quotation` / `negotiation` / `won` / `lost`. 사업장별로 영업 프로세스가 다르면 공통 단계 합의 필요

**6-4. 금액 필드 포함 여부** — Forecast를 매출액 기준으로 낼 것인지 건수 기준으로 낼 것인지에 달림. 금액을 넣으면 통화·환율 처리가 따라옴

**6-5. company 를 별도 테이블로 둘 것인가** — 기획안의 필수 필드에는 `Company` 가 텍스트로만 되어 있음. 텍스트로 두면 구현은 단순하나 "이 회사의 모든 담당자" 조회와 회사 단위 팔로업이 불가능. 위 초안은 별도 테이블을 전제함

**6-6. 첨부/브로슈어 저장 위치** — DB BLOB vs 파일 서버 + 경로 참조. 기존 `D:\FRANKONIA` 자료를 재사용한다면 후자가 자연스러움

**6-7. last_contacted_at 의 정의** — 7일 경고의 기준이 되는 값입니다. FCM을 통한 메일 발송만 반영할 것인가, 전화·방문 등 수기 기록도 반영할 것인가
