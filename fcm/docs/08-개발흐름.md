> 상태: 계획 · 갱신 2026-08-26
> 저장소: https://github.com/junhan95/FCM (현재 비어 있음)
> 인프라(VPS · Azure AD · DNS · AWS)는 junhan 이 직접 준비 · MVP 완성 후 본사 서버로 이관

## 1. ⚠️ 먼저 확인할 두 가지

### 1-1. 저장소를 비공개로 전환하는 것을 권장합니다

현재 `junhan95/FCM` 은 **공개(public)** 저장소입니다. FCM 은 4개 관할의 고객 개인정보를 다루는 사내 도구이며, 공개로 둘 때의 이득은 없고 위험은 실재합니다.

- `.env`, 접속 정보, 테스트용 실고객 데이터를 **한 번만 실수로 커밋해도 즉시 전 세계에 공개**됩니다. 커밋을 되돌려도 Git 히스토리와 각종 크롤러에 남습니다
- 격리 방식·인증 흐름·감사 로그 설계가 그대로 공개됩니다. 이 자체가 취약점은 아니지만, 굳이 공개할 이유도 없습니다
- 사업장 구조와 법인 정보가 공개 웹에 노출됩니다

> 참고: 개인 계정에서 비공개 저장소로 Pages 를 쓰려면 GitHub Pro 이상이 필요합니다. 다만 아래 §1-2 대로 FCM 에는 Pages 를 쓰지 않으므로 무관합니다.

### 1-2. GitHub Pages 로는 FCM 을 실행할 수 없습니다

Pages 는 **정적 파일만** 서빙합니다. 서버 코드가 실행되지 않습니다.

| FCM 에 필요한 것 | GitHub Pages |
|---|---|
| 로그인 · 서버 세션 검증 | ❌ 서버 코드 실행 불가 |
| PostgreSQL 연결 | ❌ |
| 매 요청 인가 검사 (E-9 주소 직접접근 차단) | ❌ 클라이언트 코드만 존재 |
| 발송 큐 · 백그라운드 워커 | ❌ |
| Graph API 자격증명 보관 | ❌ 모든 파일이 공개 다운로드 가능 |

CyberShield 는 정적 사이트였기 때문에 Pages 스테이징이 잘 동작했습니다. FCM 은 성격이 다릅니다. **인증을 클라이언트에서 처리하면 로그인 화면은 그려지지만 아무것도 지켜지지 않습니다** — 데이터가 브라우저까지 이미 내려온 상태이기 때문입니다.

또한 **저장소를 비공개로 해도 Pages 사이트 자체는 공개**입니다(접근 제어는 Enterprise Cloud 전용). 설계 문서를 Pages 에 올리면 그대로 공개 웹에 노출됩니다.

→ **결론: Pages 는 사용하지 않습니다.** GitHub 은 코드 저장소와 CI 로만 사용하고, 실행은 VPS(Docker) 에서 합니다. 설계 문서는 저장소 `docs/` 에 두어 코드와 함께 버전 관리합니다.

## 2. 저장소 구조

```
FCM/
├── docs/                     # 설계 문서 01~08 (이 문서 포함)
├── src/
│   ├── app/                  # Next.js App Router
│   │   ├── (auth)/login/     # 로그인 (유일한 미인증 진입점)
│   │   ├── (app)/            # 인증 필요 — 레이아웃에서 세션 검증
│   │   └── api/
│   ├── db/
│   │   ├── schema/           # Drizzle 스키마
│   │   ├── migrations/
│   │   ├── policies/         # RLS 정책 SQL
│   │   └── seed/
│   ├── lib/
│   │   ├── auth/             # 세션·로그인·인가
│   │   ├── tenancy/          # SET LOCAL 트랜잭션 래퍼
│   │   ├── email/            # EmailTransport (Graph / SES)
│   │   └── compliance/       # 관할별 발송 후처리
│   └── worker/               # pg-boss 워커 (별도 프로세스)
├── tests/
│   └── isolation/            # 격리 테스트 — CI 필수 통과
├── docker-compose.yml        # 로컬 개발
├── docker-compose.prod.yml   # 배포
└── .github/workflows/
```

**브랜치 전략** — 1인 개발이므로 단순하게 유지합니다.

- `main` — 항상 배포 가능한 상태
- `feat/*` — 작업 브랜치, PR 로 `main` 병합
- `v0.1.0` 형태 태그 → 배포 트리거

## 3. 환경 3단계

| 환경 | 위치 | 데이터 | 시점 |
|---|---|---|---|
| **로컬** | 개발 PC (Docker Compose) | 시드 더미 데이터만 | 지금부터 |
| **MVP / 스테이징** | junhan 관리 Hetzner Cloud VPS | 사업장 1곳 시험 데이터 | Phase 1 완료 후 |
| **운영** | 본사 서버 | 실데이터 | MVP 검증 후 |

> **실고객 데이터는 운영 환경에만 둡니다.** 로컬·스테이징에는 생성된 더미 데이터만 사용합니다. 개인정보를 개발 PC 에 복사하는 순간 그 PC 가 규제 대상이 됩니다.

**이식성 확보** — 본사 이관을 전제로 처음부터 다음을 지킵니다.

- 모든 환경 차이는 환경변수로만 표현 (코드에 호스트·경로 하드코딩 금지)
- Docker Compose 구성 하나로 어느 서버에서든 동일하게 기동
- 특정 클라우드 전용 서비스 사용 금지 (SES 는 교체 가능하도록 인터페이스 뒤에 둠)
- DB 는 `pg_dump` / `pg_restore` 로 통째 이동 가능하게 유지

## 6. CI/CD

**CI (모든 PR)**
1. 타입 체크 · 린트
2. 단위 테스트
3. **격리 테스트** — 통과하지 못하면 병합 차단
4. Docker 이미지 빌드 검증

**CD (태그 푸시)**
1. 이미지 빌드 → GitHub Container Registry
2. VPS 에서 pull → 마이그레이션 실행 → 재기동
3. 헬스체크 확인

마이그레이션은 **스키마 소유 계정**으로만 실행합니다. 애플리케이션 런타임 계정은 비소유 롤이어야 RLS 가 강제됩니다 (`07-기술스택.md` §3).
