# FCM 인증 및 접근 제어 설계

> 상태: 초안 · 갱신 2026-08-26
> **이 문서는 FCM의 최우선 설계 영역입니다.** 다른 기능은 나중에 바꿀 수 있지만, 격리와 인가 구조는 나중에 얹을 수 없습니다.

## 0. 확정된 전제

| 항목 | 결정 | 근거 |
|---|---|---|
| 사업장 간 데이터 격리 | **완전 격리** — 타 사업장 고객은 조회 불가 | 확정 |
| 사업장 간 중복 영업 | **구조상 수용** — 해결 대상 아님 | 확정 |
| 사업장 내 중복 영업 | 해결 대상 (사업장 내 고객 공유로 대응) | 가정 — 확인 요망 |
| 겸직 | **가능** — 관리자가 사업장별로 권한 부여 | 확정 |
| 동시 활성 사업장 | **세션당 1개** — 전환 시 재로그인 | 확정 |
| 계정 발급 | 신원 계정은 System Admin, 사업장 권한 부여는 Site Admin | 잠정 — 확인 요망 |
| 동시 세션 | **계정당 1개** — 새 로그인 시 기존 세션 폐기 | 잠정 |
| System Admin | 로그인은 동일하게 사업장 선택. 전사 조회는 별도 콘솔 | 잠정 — §2-5 |

## 1. 설계 원칙

1. **세션은 `(사용자, 사업장)` 쌍에 바인딩된다** — "사용자"만으로는 무엇에 접근 가능한지 결정되지 않습니다. 로그인 시점에 사업장이 고정되고 세션이 끝날 때까지 바뀌지 않습니다
2. **인가는 매 요청마다 서버에서 재검사한다** — 로그인 시 한 번 확인하고 이후 신뢰하는 방식은 세션 탈취나 권한 변경 시점에 무너집니다
3. **클라이언트는 어떤 보안 판단도 하지 않는다** — 프론트엔드의 화면 숨김과 라우터 가드는 사용성을 위한 것이며, 보안 경계가 아닙니다
4. **격리는 최종적으로 DB가 강제한다** — 애플리케이션 코드에 조건절을 빠뜨려도 데이터가 새지 않아야 합니다
5. **없는 것처럼 응답한다** — 권한 없는 리소스는 "접근 거부"가 아니라 "존재하지 않음"으로 답합니다

## 2. 로그인

### 2-1. 초기 화면
FCM의 진입점은 **로그인 화면 단일**입니다. 인증되지 않은 요청은 경로와 무관하게 로그인 화면으로 귀결됩니다.

### 2-2. 입력 요소
| 요소 | 비고 |
|---|---|
| ID | 사번 또는 회사 이메일 |
| Password | |
| 사업장 선택 | 드롭다운 — **`site` 테이블에서 동적 생성**. FRH/FRF/FRJ/FRK 는 현재 값의 예시일 뿐이며 하드코딩하지 않습니다 |

### 2-3. 검증 순서
로그인은 **세 가지를 모두** 통과해야 성립합니다.

1. 자격증명이 유효한가 (ID + PW)
2. 계정이 활성 상태인가 (`is_active`, 잠금 여부)
3. **해당 계정이 선택한 사업장에 대한 활성 권한을 보유하는가** (`user_site_membership`)

3번이 겸직 구조의 핵심입니다. FRH 담당자가 드롭다운에서 FRK를 골라도, FRK 권한이 부여되어 있지 않으면 로그인 자체가 실패합니다.

### 2-4. 실패 응답 원칙
**실패 사유를 구분해서 알려주지 않습니다.** 세 경우 모두 동일한 메시지를 반환합니다.

> "ID, 비밀번호 또는 사업장이 올바르지 않습니다."

사유를 구분하면 "이 ID는 존재하나 사업장이 틀렸다"는 정보가 새어 나가, 어떤 담당자가 어느 사업장 소속인지를 외부에서 알아낼 수 있게 됩니다. 응답 시간도 일정하게 맞춰야 같은 정보가 시간차로 새지 않습니다.

### 2-5. System Administrator 의 로그인

System Admin 은 사업장에 종속되지 않는 전사 권한이지만, **로그인 절차는 일반 사용자와 동일합니다.**

| 단계 | 일반 사용자 | System Admin |
|---|---|---|
| 사업장 선택 | 필수 | **필수 (동일)** |
| 멤버십 검사 (§2-3 3번) | 필요 | **면제** — 모든 사업장 선택 가능 |
| 세션의 `site_id` | 선택한 사업장 | 선택한 사업장 (NULL 아님) |
| 로그인 직후 보이는 것 | 해당 사업장 | **해당 사업장 (동일)** |

**핵심: System Admin 도 평소에는 한 사업장만 봅니다.** 전사 데이터는 자동으로 보이지 않습니다.

전사 조회가 필요하면 **별도의 관리 콘솔에 명시적으로 진입**해야 하며, 이때 다음이 적용됩니다.

- 진입 자체가 감사 로그에 기록됩니다
- 콘솔 내의 **모든 조회가 건별로** 감사 로그에 남습니다 (`action = cross_site_view`)
- 감사 로그의 `actor_site_id` 는 **세션의 활성 사업장**이며 NULL 이 아닙니다. 따라서 `actor_site_id ≠ target_site_id` 조건이 정상 작동해 우회 접근이 빠짐없이 탐지됩니다
- 일반 업무 화면에서는 이 경로가 열리지 않습니다 — 실수로 타 사업장 데이터를 보는 일이 발생하지 않습니다

> **이렇게 분리하는 이유:** System Admin 세션에 무제한 권한을 주면, 그 세션이 탈취될 때 전 사업장이 한꺼번에 노출됩니다. 평상시 권한을 일반 사용자와 같게 두고 전사 접근을 별도 의식적 행위로 분리하면, 노출 범위와 탐지 가능성이 모두 개선됩니다.

## 3. 세션

| 항목 | 정책 |
|---|---|
| 세션 식별자 | 추측 불가한 난수, 서버 저장 |
| 저장 방식 | HttpOnly · Secure 쿠키 (JS 접근 차단) · SameSite=`Lax` *(Strict 는 사내 메일 링크로 진입 시 재로그인을 유발하므로 §5-2(5) 와 상충)* |
| 담긴 정보 | `user_id`, **`site_id`**, `role`, 발급 시각 |
| 역할 신뢰 범위 | 세션의 `role` 은 캐시일 뿐이며, 권한이 걸린 동작은 매 요청 시 `user_site_membership` 을 재확인합니다 |
| 사업장 전환 | 세션 폐기 후 재로그인 — 세션의 `site_id` 는 변경 불가 |
| 유휴 만료 | 기본 8시간 *(가정 — 조정 가능)* |
| 절대 만료 | 기본 24시간 |
| 비밀번호 변경 시 | 해당 사용자의 다른 모든 세션 즉시 무효화 |
| 권한 회수 시 | 해당 사업장 세션 즉시 무효화 |
| **역할 변경 시** | 해당 사업장 세션 즉시 무효화 — 강등이 세션에 반영되지 않는 것을 방지 |
| 동시 세션 | 계정당 1개. 새 로그인 시 기존 세션 폐기 *(잠정)* |

> **`site_id` 를 세션에 고정하는 이유:** 요청 파라미터나 헤더에서 사업장을 받으면, 그것을 조작해 타 사업장 데이터를 요청할 수 있습니다. 사업장은 사용자가 요청마다 지정하는 값이 아니라 세션이 결정하는 값이어야 합니다.

## 4. 접근 제어 5계층

방어는 한 겹이 뚫려도 다음 겹이 막도록 겹쳐 놓습니다.

| 계층 | 대상 | 내용 | 뚫렸을 때 |
|---|---|---|---|
| **L1** 전송 | 네트워크 | HTTPS 강제, HSTS | 도청 |
| **L2** 인증 | 요청 | 유효 세션 없으면 전 경로 차단 | 익명 접근 |
| **L3** 라우트 인가 | 기능 | 역할별 기능 접근 (예: 사용자 관리는 Site Admin 이상) | 권한 상승 |
| **L4** 객체 인가 | 레코드 | `대상.site_id == 세션.site_id` 검사 | **타 사업장 데이터 유출** |
| **L5** DB | 데이터 | Row Level Security | 코드 실수 시 최종 방어 |

> **L5 를 실제로 작동시키는 두 가지 전제** — 빠뜨리면 정책이 조용히 무시되어, 최종 방어선이 아니라 유출 경로가 됩니다.
>
> 1. **`FORCE ROW LEVEL SECURITY` 를 켜고 애플리케이션은 비소유 롤로 접속** — PostgreSQL 의 RLS 는 테이블 소유자에게 기본 적용되지 않습니다. 애플리케이션이 스키마 소유 계정으로 붙으면(소규모 개발에서 흔합니다) 정책 전체가 무효화됩니다
> 2. **세션 변수는 `SET LOCAL`(트랜잭션 범위)로 설정** — 커넥션 풀 환경에서 `SET`(세션 범위)을 쓰면 이전 요청의 `site_id` 가 다음 요청에 남습니다. 하필 **타 사업장 데이터가 보이는 방향으로** 실패합니다

**L4가 가장 자주 누락되고 가장 크게 터지는 지점입니다.** L2·L3만 있으면 "로그인한 FRK 담당자가 FRH 고객 상세를 요청"하는 경우를 막지 못합니다. 로그인했고(L2), 고객 조회 권한도 있기(L3) 때문입니다.

## 5. "주소로 접근 불가" 구현 명세

요구사항의 취지는 **주소를 알아도 데이터가 나오지 않는 것**입니다. 주소를 감추는 방식은 목표를 달성하지 못합니다.

### 5-1. 하지 않을 것
- ❌ 라우트 경로를 추측하기 어렵게 짓기 — 프론트엔드 번들에 전체 라우트 표가 들어 있어 무의미합니다
- ❌ 프론트엔드 라우터 가드에만 의존 — 브라우저에서 실행되므로 우회됩니다
- ❌ 화면에서 메뉴를 숨기는 것으로 갈음 — API는 그대로 열려 있습니다

### 5-2. 할 것

**(1) 모든 데이터 조회에 세션 사업장을 강제 주입**
조회 조건은 사용자 입력이 아니라 세션에서 옵니다. 개발자가 `WHERE site_id` 를 쓰는 것을 기억해야 하는 구조가 아니라, 기본이 적용되고 벗어나려면 명시해야 하는 구조로 만듭니다.

**(2) 객체 단위 인가 (IDOR 방지)**
`/contacts/1234` 를 주소창에 직접 입력하는 경우가 요구사항이 지목한 시나리오입니다. 조회 후 소속을 검사하는 것이 아니라, 조회 자체에 사업장 조건이 포함되어야 합니다.

```
❌ contact = find(id);  if (contact.site_id != session.site_id) reject
✅ contact = find(id, site_id: session.site_id)   // 없으면 애초에 안 나옴
```

**(3) 404 응답**
타 사업장 리소스에 403(권한 없음)을 주면 "그 ID의 데이터가 존재한다"는 사실이 노출됩니다. **404(없음)로 응답**해야 존재 여부 자체가 감춰집니다.

**(4) 식별자에 UUID 사용**
연번 ID(`1, 2, 3…`)는 `/contacts/1` 부터 순차 요청해 전체를 긁는 열거 공격이 쉽습니다. 외부에 노출되는 식별자는 UUID를 권장합니다. (2·3번이 제대로 되어 있으면 데이터는 나오지 않지만, 시도 자체를 어렵게 만드는 층이 하나 더 생깁니다)

**(5) 로그인 후 원래 목적지 복귀**
미인증 상태로 `/campaigns/99` 에 접근하면 로그인 화면으로 보내고, 로그인 성공 후 그 위치로 돌아갑니다. 단 복귀 시점에도 인가는 새로 검사합니다 — 복귀 경로가 검사를 건너뛰는 우회로가 되어서는 안 됩니다.

**(6) 직접 진입 가능한 화면과 아닌 화면 구분**
발송 실행 같은 상태 변경 동작은 URL 직접 진입으로 실행되어서는 안 됩니다. 이런 동작은 GET이 아닌 POST로 처리하고 CSRF 토큰을 요구합니다.

## 6. 이상 징후 감지

다음은 정상 사용에서 발생하지 않으므로, 발생 시 감사 로그에 남기고 관리자에게 알립니다.

| 징후 | 의미 |
|---|---|
| 세션 사업장과 다른 사업장 리소스 요청 | 주소 직접 조작 시도 |
| 짧은 시간에 연속된 404 (존재하지 않는 ID 조회) | 열거 공격 |
| 동일 계정의 다른 IP 에서 반복 재로그인 | 계정 공유 또는 탈취 (동시 세션은 정책상 1개이므로 서로를 밀어냄) |
| **전사 콘솔 진입 및 타 사업장 조회** | 정상 관리 행위일 수 있으나 전수 기록 대상 |
| 로그인 실패 반복 | 무차별 대입 |
| 대량 내보내기 | 데이터 반출 |

## 7. 계정 관리

| 항목 | 정책 |
|---|---|
| 계정 발급 | **관리자 발급만** — 자가 가입 없음 *(가정)* |
| 초기 비밀번호 | 1회용 발급 후 최초 로그인 시 변경 강제 |
| 비밀번호 저장 | bcrypt / argon2 해시 (평문·단순 해시 금지) |
| 비밀번호 정책 | 최소 길이 및 복잡도 요구 |
| 로그인 실패 잠금 | 연속 실패 시 일시 잠금 |
| 퇴사 처리 | 계정 **비활성화** (삭제 금지 — 감사 로그와 발송 이력의 행위자 참조가 끊김) |
| 권한 회수 | 사업장별 개별 회수 가능 |

## 8. 선택 항목 (미결)

기본선에는 넣지 않았으나 검토 가치가 있는 것들입니다.

- **2단계 인증(2FA)** — 고객 개인정보를 다루므로 보안상 권장되나, 영업 담당자의 현장 사용 편의와 상충
- **접속 IP 제한** — 사무실·VPN 대역으로 한정. 외근·재택이 잦으면 부적합
- **Microsoft 365 SSO** — 회사 계정 체계와 통합해 별도 비밀번호 관리 부담이 사라짐. 단 메일 발송용 권한과 사용자 인증용 권한은 별개 등록이므로, "Outlook 연동하는 김에" 되는 것은 아닙니다

## 9. 확인이 필요한 사항

1. 사업장 내에서 동료의 고객을 조회할 수 있는가 (§0 가정 항목)
2. 계정 발급 주체 — System Admin 단독인가, 각 사업장 Site Admin도 가능한가
3. 세션 유휴 만료 시간 (기본 8시간이 현장 업무에 적절한가)
4. 2FA / IP 제한 도입 여부
5. Microsoft 365 SSO 사용 가능 여부 — 도입 시 §7 의 **비밀번호 관련 항목만** 불필요해집니다. 계정 발급·비활성화·사업장별 권한 부여/회수와 `user_site_membership` 은 SSO 와 무관하게 그대로 필요합니다
6. **SSO 와 "사업장 선택" 의 결합 방식** — IdP 는 사업장을 알지 못하므로 인증 이후 별도의 사업장 선택 단계가 필요합니다. 이 단계에서도 §2-4 의 사유 미구분 원칙이 지켜져야 합니다
7. 동시 세션 정책 — 계정당 1개(현재 잠정)가 맞는지. 겸직자가 두 사업장을 번갈아 봐야 하는 업무가 실제로 있는지 확인 필요
