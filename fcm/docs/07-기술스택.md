# FCM 기술 스택 결정서

> 상태: 결정 · 갱신 2026-08-26
> 확정 사항: 하이브리드 발송 · Next.js + TypeScript · 기존 자사 호스팅 활용 방향
> ⚠️ **§4 호스팅** — 기존 공유 웹호스팅으로는 실행할 수 없습니다. VPS 선정은 §4-A.

## 1. 요구사항이 이미 결정한 것

스택 선택 이전에, 앞선 문서의 확정 사항들이 선택지를 상당 부분 좁혀 놓았습니다.

| 확정 요구사항 | 강제되는 기술 조건 | 출처 |
|---|---|---|
| 격리를 **DB 레벨에서** 강제 | **PostgreSQL 필수** — MySQL·MariaDB 에는 동등 기능 없음 | E-1 |
| 세션이 `(사용자, 사업장)` 에 바인딩, 즉시 무효화 | **서버 측 세션 저장** — JWT 단독 불가 | E-7, E-15 |
| 주소 직접 입력 차단 (객체 단위 인가) | 서버에서 매 요청 인가 — **정적 사이트 불가** | E-9 |
| 감사 로그 append-only | 관계형 DB + 쓰기 전용 권한 | F-6 |
| Outlook 계정 발송 | **Microsoft Graph API** | C-2 |
| 대량 발송 분리 (하이브리드) | 전용 발송 서비스 + 발송 큐 | 확정 |
| 스프레드시트 업로드·정규화 | 서버 측 XLSX/CSV 파서 | A-1, A-2 |
| 관할별 발송 규칙 | 발송 시점 후처리 계층 | F-8~F-12 |
| 다국어 | i18n 라우팅 | G-1 |

> **가장 큰 제약은 PostgreSQL 입니다.** "DB 레벨 격리"가 기획안의 명시 요구이고, 이를 문자 그대로 만족시키는 기능(Row Level Security)은 실질적으로 PostgreSQL 에만 있습니다.

## 3. 격리 구현 — RLS 를 실제로 작동시키는 방법

RLS 를 켰다고 격리가 되지 않습니다. 다음 네 가지가 **모두** 필요합니다.

```sql
-- 1) 정책을 켜고, 소유자에게도 강제한다
ALTER TABLE contact ENABLE ROW LEVEL SECURITY;
ALTER TABLE contact FORCE ROW LEVEL SECURITY;   -- 이것이 없으면 소유자는 정책을 무시한다

-- 2) 설정이 없으면 예외를 던지게 한다 (fail-closed)
--    ⚠️ current_setting('app.site_id') 만으로는 부족하다. PostgreSQL 은 한 번
--    설정된 사용자 정의 파라미터를 제거하지 않고 ''(빈 문자열)로 되돌리므로,
--    "미설정 시 예외"가 성립하지 않고 캐스팅 오류로 우연히 막힌다.
--    실측으로 확인된 사항이다 — docs/09-phase0-검증.md §2
CREATE OR REPLACE FUNCTION current_site_id() RETURNS uuid
  LANGUAGE plpgsql STABLE AS $$
DECLARE v text;
BEGIN
  v := current_setting('app.site_id', true);
  IF v IS NULL OR v = '' THEN
    RAISE EXCEPTION 'app.site_id 가 설정되지 않았습니다'
      USING ERRCODE = 'insufficient_privilege';
  END IF;
  RETURN v::uuid;
END $$;

CREATE POLICY site_isolation ON contact
  USING (site_id = current_site_id())
  WITH CHECK (site_id = current_site_id());   -- WITH CHECK 없으면 쓰기가 뚫린다
```

```ts
// 3) 애플리케이션은 비소유 롤로 접속한다 (마이그레이션 계정과 분리)
// 4) 요청마다 트랜잭션 안에서 설정한다
//    SET LOCAL 은 파라미터 바인딩을 지원하지 않는다. 문자열 결합으로 만들면
//    SQL 인젝션 경로가 되므로 set_config(..., is_local=true) 를 쓴다.
await db.transaction(async (tx) => {
  await tx.execute(sql`select set_config('app.site_id', ${session.siteId}, true)`);
  return tx.select().from(contact);        // 정책이 자동 적용됨
});
```

**`SET LOCAL` 이어야 하는 이유:** `SET`(세션 범위)을 쓰면 커넥션 풀에서 커넥션이 반환될 때 값이 남습니다. 다음 요청이 그 커넥션을 받으면 **이전 사용자의 사업장으로 조회**됩니다. 하필 타 사업장 데이터가 보이는 방향으로 실패합니다. `SET LOCAL` 은 트랜잭션 종료 시 자동으로 사라집니다.

> **검토한 대안 — 사업장별 스키마 분리**
> `frh.contact`, `frk.contact` 처럼 스키마를 나누는 방식도 유효합니다. 격리가 정책이 아니라 구조로 보장되고, 향후 특정 사업장 데이터를 별도 위치에 두어야 할 때(예: 중국 규제 변경) 유리합니다.
> 채택하지 않은 이유: 마이그레이션을 5회 반복해야 하고, 두 방식 모두 결국 요청마다 `SET LOCAL`(search_path 또는 site_id)을 요구해 복잡도 이득이 크지 않습니다. **사업장별 데이터 소재지 분리가 필요해지면 그때 전환을 검토합니다.**

## 4. 호스팅

"기존 자사 서버 활용"으로 정하셨는데, 확인해야 할 문제가 있습니다.

**현재 서버가 이 애플리케이션을 실행할 수 없을 가능성이 높습니다.**

`Web Design\Access\Access.docx` 의 접속 정보에서 서버가 `www436.your-server.de` 로 확인됩니다. 이는 **Hetzner 공유 웹호스팅(Webhosting)** 입니다. CyberShield 는 정적 사이트를 SFTP 로 업로드하는 방식이라 이 환경에서 문제없이 동작했습니다.

FCM 은 다릅니다.

| 필요한 것 | 공유 웹호스팅 |
|---|---|
| PostgreSQL | ❌ MySQL/MariaDB 만 제공 |
| 상시 실행 Node 프로세스 | ❌ (Webhosting L 의 Node.js 기능은 제한적) |
| 백그라운드 워커 (발송 큐) | ❌ 장시간 프로세스 불가 |
| Docker | ❌ |
| SSH·root | ❌ |

→ **CyberShield 와 같은 서버에 올릴 수는 없습니다.** FCM 은 정적 사이트가 아니라 DB 와 백그라운드 작업이 필요한 애플리케이션입니다.

### 4-A. VPS 선정 (2026-08 조사)

> ⚠️ **Hetzner 가 2026년 상반기에 가격을 인상했습니다.** 이 문서의 이전 판에 적힌
> "CX22 약 €4.35/월" 은 인상 전 수치이며 더 이상 유효하지 않습니다.
> 인상폭은 계열별로 크게 달랐습니다 — CX(x86 공유) +31~38%, CAX(ARM) +30%,
> **CPX(AMD) +144~175%**, CCX(전용) +113~173%. 주문 시점에 실제 가격을 재확인하십시오.

#### 필요 사양 산정

| 부하 요인 | 규모 |
|---|---|
| 동시 사용자 | 10~20명 (5개 사업장 합계) |
| 데이터 크기 | 고객 연락처 수천~수만 행 — 수백 MB 수준 |
| 상주 프로세스 | Next.js 서버 · pg-boss 워커 · PostgreSQL · Caddy |
| 트래픽 | 내부 업무 도구 — 무시 가능 |

CPU·트래픽은 문제가 되지 않습니다. **메모리가 유일한 실질 제약**이며,
PostgreSQL 공유 버퍼 + Node 힙 + 워커가 동시에 올라가므로 4GB 는 빠듯하고
8GB 면 여유가 있습니다. 이미지 빌드는 CI 에서 하고 서버는 pull 만 하므로
빌드 메모리는 계산에 넣지 않습니다.

#### 후보 비교

| 제공사 | 소유 | 인증 | AVV | 비고 |
|---|---|---|---|---|
| **Hetzner** | 독일 | ISO 27001 · **BSI C5** | 공개 | 스냅샷·자동백업·방화벽·인플레이스 리사이즈 |
| netcup | 독일 | ISO 27001 | 공개 | 디스크가 훨씬 큼, 대신 클라우드 부가기능 없음 · 리사이즈 시 마이그레이션 필요 |
| IONOS | 독일 | ISO 27001 · BSI C5 | 공개 | 기업향, 상대적 고가 |
| Contabo | **미국 PE(KKR·Oakley) 소유** | — | — | 뮌헨 소재이나 **소유 구조상 CLOUD Act 노출** |
| DigitalOcean · Vultr · Linode · AWS | 미국 | — | — | EU 리전이어도 소유·모회사 기준 CLOUD Act 적용 |

> **소재지만으로는 부족합니다.** 서버가 프랑크푸르트에 있어도 모회사가 미국 법인이면
> 미국 CLOUD Act 의 적용 대상입니다. FRH·FRF 가 독일 법인이고 GDPR 이 적용되는
> 프로젝트이므로, **EU 소유 + 공개 AVV** 를 기본 조건으로 둡니다.

**Hetzner 를 고른 이유 네 가지**

1. **이미 거래 중입니다.** CyberShield 가 Hetzner 공유 웹호스팅에 있으므로
   계정·청구·AVV 가 하나로 유지됩니다. 새 벤더 심사가 필요 없습니다
2. **BSI C5 인증** — 독일 연방정보보안청 기준입니다. 본사 법무·감사 대응 시
   설명이 가장 짧아지는 항목입니다
3. **운영 도구** — 자동 백업, 스냅샷, 방화벽, **인플레이스 리사이즈**.
   netcup 은 사양 변경 시 마이그레이션이 필요합니다. 운영 중인 시스템에서 이 차이는 큽니다
4. **오프사이트 백업 경로** — Storage Box 로 DB 덤프를 서버 밖에 보관할 수 있습니다.
   같은 서버 안의 백업은 서버가 죽으면 함께 죽습니다 (요구사항 G-2)

**채택하지 않은 것**

- **CPX·CCX 계열** — 2026년 인상으로 가격이 2~2.7배가 되었습니다. 이 워크로드가
  전용 vCPU 를 필요로 하지 않습니다
- **ARM(CAX21, €10.49)** — 동급 x86 보다 월 €1 저렴하나, 멀티아치 이미지 빌드와
  네이티브 모듈(`@node-rs/argon2`) 아키텍처 확인이 따라옵니다.
  **월 €1 를 위해 감수할 마찰이 아닙니다.** 규모가 커지면 재검토합니다
- **netcup** — 같은 값에 디스크가 3배지만, FCM 은 디스크가 병목이 아닙니다.
  운영 도구 쪽이 더 중요합니다
- **Contabo 및 미국계 제공사** — 위 표 참조

#### 주문 시 함께 설정할 것

1. **자동 백업 활성화** (주문 시 체크) — 나중에 켜도 되지만 잊기 쉽습니다
2. **방화벽** — 22(SSH, 가능하면 본인 IP 로 제한) · 80 · 443 만 개방.
   **PostgreSQL 5432 는 절대 외부에 열지 않습니다** — Docker 네트워크 내부로만
3. **SSH 키 인증만 허용**, 비밀번호 로그인 비활성화
4. **오프사이트 백업** — `pg_dump` 를 암호화해 Storage Box 로. 서버 스냅샷과는 별개입니다
5. **AVV(Auftragsverarbeitungsvertrag) 체결** — Hetzner 콘솔에서 전자 서명 가능.
   GDPR 제28조상 수탁처리자와의 계약은 **선택이 아니라 의무**입니다
6. 배포 전 스냅샷 — 몇 센트짜리 보험입니다

#### 본사 이관 시

Docker Compose 구성이므로 본사 서버로 옮길 때 애플리케이션은 그대로 갑니다.
필요한 것은 `pg_dump` / `pg_restore` 와 DNS 전환뿐입니다.
이 이식성 때문에 특정 클라우드 전용 관리형 서비스(관리형 DB 등)를 쓰지 않았습니다.

### 4-B. 본사 서버로 Cloud VPS 를 대체할 수 있는가 (2026-08 검토)

#### 먼저 — VPS 는 PostgreSQL 때문에 있는 것이 아닙니다

FCM 의 상시 구동 요소는 넷입니다.

| 구성 요소 | 성격 | 어디서든 되는가 |
|---|---|---|
| PostgreSQL | 상태 저장 | **가장 쉬움** — 내부망 어디든 |
| Next.js 서버 | 매 요청 인가·SSR | **공개 HTTPS 엔드포인트 필요** |
| pg-boss 워커 | 백그라운드 발송 (Phase 3) | 아웃바운드만 필요 |
| Caddy | TLS 종단 | 공개 노출 지점 |

VPS 가 제공하는 것은 **5개국 사업장이 접속할 수 있는, 상시 켜져 있는 공개 HTTPS
서버**입니다. PostgreSQL 은 이 중 가장 작고 옮기기 쉬운 조각입니다.

따라서 "본사 서버에 PostgreSQL 만 두고 VPS 를 없앤다" 는 성립하지 않습니다.
성립하는 것은 **"본사 서버에 전부 둔다"** 입니다.

#### DB 만 본사에 두고 앱을 밖에 두는 구성은 피해야 합니다

| 문제 | 내용 |
|---|---|
| **PostgreSQL 을 인터넷에 노출** | 5432 를 외부에 여는 것 — §4-A 주문 체크리스트에서 명시적으로 금지한 항목입니다 |
| 지연 | 매 요청이 트랜잭션 + `SET LOCAL` 로 최소 2회 왕복합니다. 인터넷 구간이 끼면 체감 성능이 떨어집니다 |
| 운영 이중화 | 두 곳을 다 관리하면서 이득은 없습니다 |
| 장애 지점 증가 | 둘 중 하나만 끊겨도 서비스가 멈춥니다 |

앱과 DB 는 같은 네트워크 안에 두는 것이 옳습니다.

#### 그래서 실제 질문은 하나입니다

> **본사 서버가 5개국에서 접속 가능한 HTTPS 를 받을 수 있는가?**

| 답 | 결론 |
|---|---|
| **인바운드 가능** (공인 IP 또는 DMZ) | ✅ **VPS 불필요. 전부 본사 서버로.** 추가 비용 €0 |
| 인바운드 불가, 아웃바운드 가능 | 터널 필요 → 아래 §선택지 |
| 완전 폐쇄망 | 5개국 접속 불가. 전원 VPN 배포가 필요해 현실적으로 어려움 |

#### 인바운드가 막혀 있을 때의 선택지

**(a) 소형 EU VPS 를 릴레이로** — 권장

본사 서버가 VPS 로 아웃바운드 WireGuard 터널을 열고, VPS 는 리버스 프록시만 합니다.
본사 방화벽에 인바운드 규칙을 요청하지 않아도 되며, 데이터는 EU 안에 머뭅니다.

- CX23 (2 vCPU/4GB) €5.49 + IPv4 €0.50 → **부가세 포함 월 약 €7**
- 애플리케이션과 DB 는 본사에, 공개 지점만 밖에 둡니다
- CX33 단독 운영(월 €17) 대비 절반 이하

**(b) Cloudflare Tunnel** — 이 프로젝트에는 권하지 않습니다

아웃바운드 연결만으로 공개할 수 있어 기술적으로는 가장 간편합니다. 다만
**TLS 가 Cloudflare 엣지에서 종단**되므로 고객 개인정보가 평문으로 미국 기업의
인프라를 통과합니다. §4-A 에서 소유 구조를 이유로 미국계 제공사를 제외한 판단과
일관되지 않습니다.

**(c) 사내 VPN 전원 배포** — 5개국·10~20명 규모에서 운영 부담이 큽니다

> 그 장비가 죽으면 함께 죽습니다 (요구사항 G-2).

#### 본사 IT 에 확인할 것

기술 사양보다 **운영 책임**이 더 중요한 질문입니다.

**접속**
1. 공인 IP 또는 DMZ 로 인바운드 443 을 받을 수 있는가
2. 불가하다면 아웃바운드 연결(WireGuard 등)은 허용되는가
3. 서버가 어느 나라에 있는가 — GDPR 소재지 판단에 직결

**실행 환경**
4. OS 와 Docker(또는 Podman) 사용 가능 여부
5. 가용 메모리 — 최소 4GB, 8GB 권장
6. 디스크 여유 — 초기 20GB 면 충분

**운영 — 여기가 핵심입니다**
7. **누가 운영하는가** — 재기동·패치·장애 대응 주체
8. 백업 정책이 이미 있는가, FCM 도 그 대상에 포함되는가
9. **24시간 가동인가** — 야간·주말 정지가 있으면 5개국 시차상 문제가 됩니다
10. 사양 변경이나 재기동을 요청하면 얼마나 걸리는가
11. 개발자(junhan)에게 SSH 접근이 주어지는가, 아니면 매번 요청해야 하는가

11번이 실제로는 가장 중요합니다. **접근이 요청 기반이면 배포 한 번에 며칠이
걸릴 수 있고, 그러면 개발 속도가 본사 IT 의 응답 속도에 묶입니다.**

#### 권고

1. **인바운드 HTTPS 가 가능하고 SSH 접근이 주어진다면** — 본사 서버로 바로 가는 것이
   맞습니다. 비용도 소재지도 더 낫습니다
2. **확인에 시간이 걸린다면** — VPS 로 MVP 를 먼저 띄우고 병행 확인합니다.
   Docker Compose 구성이라 이관 비용이 낮습니다 (`pg_dump` + DNS 전환)
3. **어느 쪽이든 개발·스테이징 환경은 분리해 두어야 합니다.** 운영 서버에서
   마이그레이션을 시험하지 않습니다. 현재는 로컬 환경이 그 역할을 합니다

## 5. 인증을 직접 구현하는 이유

일반적으로는 검증된 라이브러리를 쓰는 것이 옳습니다. 여기서는 반대입니다.

| 요구사항 | 표준 라이브러리와의 관계 |
|---|---|
| ID + PW + **사업장 선택** 3요소 로그인 | 표준 아님 — 어느 라이브러리도 지원 안 함 |
| 세션이 `(사용자, 사업장)` 에 바인딩 | 표준 세션은 사용자만 담음 |
| 실패 사유 미구분 + 응답 시간 균일화 | 라이브러리 기본 동작과 충돌 |
| 권한·역할 변경 시 세션 즉시 무효화 | JWT 기반 라이브러리는 불가 |
| 계정당 활성 세션 1개 | 직접 관리 필요 |

Auth.js 같은 라이브러리를 쓰면 요구사항 대부분을 우회 구현하게 되어, 결국 직접 구현하면서 라이브러리 제약까지 떠안습니다.

**단, 암호학은 직접 만들지 않습니다.**

- 비밀번호 해싱: `@node-rs/argon2` (Argon2id)
- 세션 ID: `crypto.randomBytes(32)`
- 쿠키: HttpOnly · Secure · SameSite=Lax
- 세션은 DB 테이블(`user_session`)에 저장 — 즉시 무효화 가능

구현 범위는 로그인·로그아웃·세션 검증 미들웨어로 크지 않으며, 요구사항이 전부 커스텀이라 오히려 단순합니다.

## 6. 메일 발송 — 하이브리드 구조

두 경로를 하나의 인터페이스 뒤에 둡니다.

```
EmailTransport (인터페이스)
├── GraphTransport   → sales@frankoniagroup.com   (1:1 팔로업, 소량)
└── SesTransport     → news.frankoniagroup.com    (대량 캠페인)
```

### 6-1. 개별 발송 — Microsoft Graph API

- Azure AD 앱 등록 + **애플리케이션 권한** `Mail.Send`
- **`ApplicationAccessPolicy` 로 `sales@` 단일 사서함으로 제한** — 이것을 하지 않으면 앱이 조직의 **모든** 사서함에서 메일을 보낼 수 있는 과도한 권한을 갖게 됩니다
- 자격증명은 `system_setting` 에 암호화 저장, 되읽기 불가 (C-14)
- 한도: 30통/분, 1만 수신자/일 — 개별 발송에는 충분

### 6-2. 대량 발송 — Amazon SES (eu-central-1)

**Exchange Online 을 쓰지 않는 이유는 Microsoft 자신의 권고입니다.** 공식 문서는 "뉴스레터 등 정당한 대량 상업용 메일이 필요한 고객은 이를 전문으로 하는 서드파티 제공자를 사용해야 한다"고 명시합니다. 여기에 최근 도입된 테넌트 단위 외부 수신자 한도(TERRL)가 라이선스 수에 따라 추가로 적용됩니다.

실질적 위험은 한도가 아니라 **도메인 평판**입니다. 견적·계약 메일을 보내는 `frankoniagroup.com` 으로 대량 발송을 하다 스팸 신고가 누적되면, 영업 메일 자체가 스팸함으로 갑니다.

| 항목 | 내용 |
|---|---|
| 리전 | eu-central-1 (프랑크푸르트) — EU 내 유지 |
| 비용 | 1,000통당 약 $0.10 |
| 발신 도메인 | **`news.frankoniagroup.com`** — 본 도메인과 평판 분리 |
| 인증 | 서브도메인에 SPF · DKIM · DMARC 개별 설정 |
| 반송·불만 처리 | SNS 웹훅 → `send_log.status` 자동 갱신 (C-10) |

대안: **Brevo**(프랑스) — EU 사업자를 선호할 경우. 관리 UI 가 있으나 비용이 높고 제어가 적습니다.

### 6-3. 관할별 후처리

발송 직전에 `site.jurisdiction` 을 읽어 적용합니다 (F-8~F-12).

```
if (jurisdiction === 'kr') subject = '(광고)' + subject;   // 변칙 표기 금지
body += unsubscribeFooter(jurisdiction, locale);           // KR 은 비용 미부담 고지 포함
```

제목·본문 원문은 그대로 저장하고, **변형은 발송 시점에만** 적용합니다.

### 7-A. Supabase 검토 결과 — 채택하지 않음 (2026-08)

"본사 서버 + Supabase" 조합을 검토했습니다. 세 가지 형태로 나눠 평가했습니다.

| 형태 | 구성 | 평가 |
|---|---|---|
| A | 본사 서버(앱) + **Supabase Cloud**(DB·Auth) | ✕ 요구사항 충돌 + 관할 문제 |
| B | 본사 서버에 **Supabase 셀프호스팅** | ✕ 운영 부담이 이득보다 큼 |
| C | 본사 서버 + **현재 스택 그대로** | ✅ 기존 계획 (Phase 5) |

#### 결정적 충돌 네 가지

**1. 세션 즉시 무효화가 불가능합니다 (E-15 · E-25 위반)**

Supabase Auth 는 액세스 토큰이 JWT 이며 **만료 전에는 무효화할 수 없습니다.**
공식 문서가 이를 명시합니다 — 세션 설정을 바꿔도 "다음 갱신 시점에야 검사가
적용"되며, 기본 만료는 1시간입니다.

우리 요구사항은 **권한 회수·역할 변경 시 즉시 무효화**입니다. 최대 1시간 동안
회수된 권한으로 타 사업장 데이터에 접근할 수 있다면 격리 요구가 성립하지 않습니다.

Supabase 문서가 제시하는 우회책은 "민감한 작업에서는 `session_id` 를
`auth.sessions` 테이블과 대조하라" 입니다. **그것은 우리가 이미 구현한 방식입니다**
(`resolveSession()` 이 매 요청 `user_site_membership` 을 재확인). 즉 Supabase Auth 를
얹은 뒤 그것을 우회해서 우리 방식으로 돌아가는 구조가 됩니다.

**2. 로그인 3요소가 Supabase Auth 의 모델에 없습니다**

`ID + 비밀번호 + 사업장 선택` 은 표준 인증 흐름이 아닙니다. 사업장을 커스텀 클레임으로
넣고 전환 시마다 토큰을 재발급하는 구조를 별도로 만들어야 하며, 그러면 Supabase Auth 를
쓰는 이득이 사라집니다. **실패 사유 미구분과 응답 시간 균일화**(§docs/05 §2-4)도
Supabase Auth 의 기본 응답과 맞지 않습니다.

**3. RLS 모델이 다르고, 우리 쪽이 이 용도에 더 안전합니다**

| | Supabase 방식 | FCM 방식 |
|---|---|---|
| DB 접근 주체 | **클라이언트가 직접** (JWT 지참) | 서버만 |
| RLS 판단 근거 | JWT 클레임 (`auth.uid()`) | 서버가 설정한 `app.site_id` |
| 클라이언트가 DB 에 도달 | 가능 | **불가능** |

Supabase 의 설계는 클라이언트가 DB 와 직접 대화하는 것을 전제로 합니다. 편리하지만,
**최우선 요구가 격리인 시스템에서 DB 를 클라이언트에 노출하는 것은 공격면을 넓히는
방향**입니다. 현재 구조는 브라우저가 DB 에 닿을 수 없습니다.

**4. 관할 — 두 턴 전 결정과 모순됩니다**

Supabase 는 미국 법인이며 **AWS 위에서 운영**됩니다. EU 리전(프랑크푸르트 등)을
고를 수 있고 DPA 도 제공하지만, 공식 문서 스스로 "백업·로그·외부 반출 데이터·
Edge Function 실행·하위 수탁자가 데이터 소재지와 국외 이전 분석에 영향을 준다"고
밝힙니다.

VPS 선정(§4-A)에서 "소재지만으로는 부족하고 소유 구조가 결정한다"는 이유로
미국계 제공사를 제외했습니다. Supabase Cloud 를 쓰면 같은 노출을 다른 문으로
들이는 셈입니다.

#### 형태 B (셀프호스팅)를 택하지 않는 이유

Supabase 셀프호스팅은 Docker Compose 로 **8개 안팎의 컨테이너**를 띄웁니다 —
PostgreSQL, GoTrue(인증), PostgREST(API), Realtime, Storage, Kong(게이트웨이),
Studio, Analytics.

FCM 이 실제로 필요한 것은 **PostgreSQL 하나**입니다. PostgREST 는 Next.js 서버가
대신하고, GoTrue 는 위 §1·2 때문에 쓸 수 없으며, Realtime·Kong 은 쓰지 않습니다.

게다가 셀프호스팅은 **관리형 백업과 PITR 을 잃습니다** — `pg_dump` 나 WAL 아카이빙을
직접 스크립트로 짜야 합니다. 그것은 현재 계획과 동일한 작업량입니다. 즉 운영 대상
컨테이너가 4개에서 11개로 늘어나는 대신 얻는 것은 Studio GUI 하나입니다.

10~20명이 쓰는 내부 도구에 맞는 교환이 아닙니다.

#### 공정하게 — Supabase 가 실제로 좋은 지점

- **Storage** — 브로슈어·첨부파일 보관에 쓸 만합니다. 다만 파일시스템이나
  S3 호환 스토리지로도 충분하며, 이것 하나 때문에 스택 전체를 바꿀 이유는 없습니다
- **Studio** — 임시 SQL 조회에 편리합니다. pgAdmin·DBeaver 로 대체됩니다
- **관리형 백업·PITR** — 진짜 가치가 있습니다. 단 PITR 은 7일 보존 기준 월 $100 이며,
  Pro 요금제 자체는 월 $25 부터입니다
- **인증을 직접 만들지 않아도 되는 것** — 일반적인 프로젝트라면 큰 이점입니다.
  이 프로젝트는 인증 요구가 전부 비표준이라 해당하지 않습니다

> **일반론으로는 Supabase 가 좋은 선택입니다.** 채택하지 않는 이유는 제품의 문제가
> 아니라, 이 시스템의 확정 요구사항(즉시 무효화 · 3요소 로그인 · 클라이언트의 DB 미도달 ·
> EU 소유)과 맞지 않기 때문입니다.

#### 관리형 PostgreSQL 이 필요해지면

운영 부담을 줄이고 싶어지는 시점이 오면, Supabase 가 아니라 **EU 소유 관리형
PostgreSQL** 을 검토합니다 — Scaleway(프랑스), Aiven(핀란드), IONOS(독일) 등.
애플리케이션 코드는 그대로이며 접속 문자열만 바뀝니다. 현재 구조가 관리형 서비스에
종속되지 않도록 설계된 이유입니다.

다만 10~20명 규모에서는 Docker 안의 PostgreSQL 로 충분하며, `pg_dump` 를 오프사이트로
보내는 것만 확실히 하면 됩니다.
